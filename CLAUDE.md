# Couplet
React Native coupon wallet - aggregates coupons from multiple sources, supports P2P sharing.

## Architecture
Hybrid: client-server (auth/metadata/notifications) + P2P (coupon transfer).
**Security invariant: coupon codes, QR codes, barcodes are NEVER stored on or transmitted through the server. Server holds metadata only. Enforce this in all code. Two carve-outs, both in the Gmail scanner (feature 8), both server-side/transient/never persisted to `GmailConnection.candidates` (headers only): (1) `extractCouponFields` returns a parsed `code` field in the `/scan` and `/extract` responses; (2) `GET /gmail/candidates/:messageId/body` returns the raw email body (may contain the code in plain text), capped at 4000 chars. No other path may send a code through the server.**
Server coordinates P2P sessions but never relays coupon data.
**Coupon-code transfer staging:** Stage 2 (current, **runs in plain Expo Go - no dev build**) - on share, the server checks each recipient's live connections and returns `online_recipient_ids` in the share response; the sharer's client then negotiates a WebRTC `RTCDataChannel` per online recipient (SDP/ICE relayed opaquely by the server's WS `$default` route, actions `webrtc-offer`/`webrtc-answer`/`webrtc-ice-candidate`/`webrtc-cancel` - see `server/src/ws/handler.ts`, `client/services/webrtc.ts`) and sends the code directly over it - the server never sees it. **The `RTCPeerConnection`s do not run in React Native** - `react-native-webrtc` was rejected because it needs a custom dev client (which needs a Mac or paid Apple account). Instead they run inside a hidden 1×1 `<WebView>` mounted once at the app root (`client/components/WebRTCBridge.tsx`) loading an inline page (`client/services/webrtcBridgeHtml.ts`); `client/services/webrtc.ts` drives it via `injectJavaScript` (payloads double-`JSON.stringify`d so codes can't break out of the script) and receives results via `postMessage`. The page needs `baseUrl: 'https://localhost'` to be a secure context, and the WebView needs a non-zero size and an `onMessage` handler or the bridge silently dies. Offline members still get the code persisted on their group_share notification as a fallback, now AES-256-GCM encrypted at rest (`server/src/lib/codeCrypto.ts`) with a 72h DynamoDB TTL (`expires_at`; the same attribute gives every other notification 30-day retention); the same mechanism is also used as a rescue path (`POST /groups/:id/coupons/:couponId/rescue-code`) when a P2P negotiation to an online recipient fails. Consumed fallback/rescue codes are cleared immediately via `DELETE /notifications/:id/code`, ahead of the TTL. Never add coupon_code to WS notification payloads (`notifyUser` strips it) or to signaling frames (server never inspects `sdp`/`candidate` contents). Known limitation: no TURN server - P2P can fail behind symmetric/carrier-grade NAT, mitigated by the rescue path.

**Barcode/QR image transfer (P2P only):** a coupon's barcode/QR image is a coupon code in visual form, so it takes the identical P2P path and **has no server-side fallback of any kind** - the encrypted-code fallback must never be extended to it. Encoded on the sharer with `expo-image-manipulator` (already a dependency - do not add `expo-file-system`) to a downscaled base64 JPEG (`encodeCouponImageForTransfer`, `client/services/couponSharing.ts`; max width 1000px because a barcode needs horizontal resolution to stay scannable, unlike the ~256px avatars), then chunked over the same `RTCDataChannel` in 16KB frames with `bufferedAmount` backpressure (`sendImage` in `webrtcBridgeHtml.ts`). Framing: header `{coupon_id, code, has_image}` (code may be null - image-only coupons are now shareable), then `{img, i}` chunks, then `{img_end, n}`. The recipient reassembles by index and **checks completeness before handing anything to RN** - an incomplete image is dropped rather than persisted, so no ack goes out, the sharer times out, and the code still lands via the rescue path. **The ack is only sent after code AND image are both persisted** (`webrtc.ts`'s `received` case), preserving the persist-before-ack ordering. Received images are stored as `data:image/jpeg;base64,...` under the same `coupon_image_` AsyncStorage key that a locally-added `file://` URI uses, so every read path works unchanged. Timeouts step up once the channel opens (page 15s negotiation -> 30s transfer; RN watchdog 25s -> 45s) - the page posts `transferring` so the recipient's RN watchdog extends too, since only the header reveals an image is coming. `inspectShareable` now reports `imageOnly`, and `shareWarning` (replaces `unusableShareMessage`) warns that offline members won't get an image-only coupon until a re-share.

**Code updates after sharing:** editing a coupon's code (`CouponEditForm`) doesn't touch the server at all for the code itself - same invariant as the original share - so the server can never detect the edit on its own. `GET /coupons/:id/groups` (owner-only) tells the owner's client which groups the coupon is already shared to; the client then redelivers via `deliverCouponCode` (`client/services/couponSharing.ts`, shared with the original share flow) to each. `POST /groups/:id/coupons/:couponId` takes `code_updated: true` for this: online recipients get the new code purely via P2P, no DB row at all; offline recipients get a `coupon_code_sync` row (encrypted, 72h TTL - identical mechanics to `group_share`'s fallback) marked `read: true` and filtered out of the panel/banner/OS-notification/catch-up paths client-side (`dispatchServerNotification`'s type guard, `NotificationsContext.tsx`) so it never surfaces as "New coupon" for something that wasn't newly shared - an edit is a correction, not an event, same principle as the silent metadata refresh (`coupon_updated`) above. Both `group_share` and `coupon_code_sync` are consumed identically wherever a fallback code is picked up (index.tsx's `load()`, the group screen's `handleOpenCouponDetail` - the latter checks unconditionally for `coupon_code_sync`, not gated behind "no local code yet", since an update must overwrite an existing stale code).

## Tech Stack
| Layer | Tech |
|---|---|
| Mobile | React Native |
| Backend | Node.js + Express on **AWS Lambda** (serverless, via `serverless-http`) |
| API Gateway | AWS API Gateway HTTP API - public URL, routes all requests to Lambda |
| Auth | AWS Cognito (issues JWTs for all API calls) |
| Notifications | In-app + live via API Gateway **WebSocket** (push token / SNS not usable in Expo Go) |
| Real-time | API Gateway **WebSocket API** + Lambda - live notifications + WebRTC signaling relay; `Couplet-Connections` table (PK `connection_id`, GSI `user_id-index`) |
| P2P | Browser WebRTC inside a hidden `react-native-webview` (Expo-Go-bundled, **no native build**) - signaling reuses the WebSocket API's `$default` route, no TURN server (STUN only) |
| Database | AWS DynamoDB |
| Gmail scanner | Google OAuth 2.0 (PKCE + backend code exchange) + Gmail API `gmail.readonly` |

## Data Model
**Server - Users:** `user_id, email, user_name, password_hash, created_at, coupon_id_list, phone_number, profile_image` (phone_number = second identity for login/member-search; profile_image = small base64 data-URL avatar ~256px, set via `PUT /auth/me/photo`, exposed to group members as their `image`)
**Server - Coupon (metadata only):** `coupon_id, owner_id, category, redeemable_stores, expiration_date, balance, status, giftcard_url`
**Server - Group:** `group_id, name, user_id_list, pending_user_ids, coupon_id_list, admin_user_id, image` (image = small base64 data-URL avatar ~256px, shared with all members; admin-set via `PUT /groups/:id/photo`)
**Server - GmailConnection:** `user_id (PK), gmail_email, refresh_token_encrypted, oauth_client, last_scan, created_at, candidates` - refresh token is AES-256-GCM encrypted app-side (`server/src/lib/tokenCrypto.ts`), not AWS KMS (Learner Lab's fixed `LabRole` can't create KMS keys - swap in real KMS if this moves off Learner Lab); `oauth_client` (`'native' | 'web'`) records which Google OAuth client issued the refresh token (Google rejects refreshing it with the other client's credentials); `candidates` is a list of `{message_id, from, subject, date, created_at}` kept on the same row (one user's filtered inbox is small), merged by `message_id` on each scan so re-scans upsert instead of duplicating
**Client local storage:** coupon code / QR / barcode, owner identifier, sharing permissions; Gmail draft coupon fields (`gmail_draft_<message_id>`) and dismissed-draft flags (`gmail_dismissed_<message_id>`), see `client/storage/gmailDraftStorage.ts`

## Features
1. Auth - register/login via Cognito (email or phone as identity), JWT on all requests; editable profile (username, phone, photo) via `PATCH /auth/me` + `PUT /auth/me/photo`. Signup requires email verification - Cognito confirm-signup flow, client-direct via `amazon-cognito-identity-js` (`client/services/cognito.ts`: `cognitoConfirmSignUp`/`cognitoResendConfirmationCode`), no server involvement. Account is `UNCONFIRMED` (unusable) until the emailed code is entered; login on an unconfirmed account re-triggers confirmation instead of failing dead-end (`client/app/(auth)/login.tsx`). **SRP login must finish inside Cognito's 30s `PASSWORD_VERIFIER` challenge window** (measured: 29s authenticates, 31s does not). Expo Go has no `RNAWSCognito` native accelerator, so `amazon-cognito-identity-js` falls back to pure-JS jsbn `modPow`, which took ~31s on Android and ~13s on iOS - Android answered after expiry and Cognito reported it as `NotAuthorizedException: Incorrect username or password`, indistinguishable from a wrong password. `client/services/srpFastMath.ts` replaces `BigInteger.prototype.modPow` with native Hermes `BigInt` (~1-2s, jsbn kept as fallback); it must be invoked after the `amazon-cognito-identity-js` import so it overrides `enhance-rn.js`'s wrapper. Never switch to `USER_PASSWORD_AUTH` for speed - it puts the password in the request body and there is no speed left to gain.
2. Coupon storage - codes stored locally, metadata synced to server
3. Coupon management - add/view/update, filter by category or expiry, status: `active/expired/used`; optional `giftcard_url` for dynamic web-link gift cards (e.g. BuyMe) - opens in-app browser via `expo-web-browser`; server stores URL as metadata (not a coupon code - invariant preserved). `CouponDetail` is opened by non-owners too (to redeem a shared coupon from the group screen) - it derives `isOwner` from `useAuth` and hides edit/share/delete for non-owners, since those are owner-gated server-side. Keep any new owner-only control behind that flag rather than leaving it as a dead end.
4. Notifications - live over WebSocket while app open (group_invite/group_share/coupon_revoked/coupon_used/coupon_partial_redeem pushed via `notifyUser`). Separately, `pushCouponUpdated` sends a **live-only** `coupon_updated` WS event (via `pushToUser`, no notification row/banner/OS alert) when a shared coupon's metadata is edited - the need there is fresh data, not an alert; the client just calls `bump()`. Use that pattern for any future "refresh, don't interrupt" signal. In-app banner when on-screen, **local OS notification** (`expo-notifications`, works in Expo Go) when app backgrounded/not focused; catch-up poll on resume fires OS notifications for items missed while suspended (baseline-suppressed on cold start); clickable rows + OS-notification taps delete + deep-link to `/group/[id]`. Expiry alerts still client-generated. True remote push when app closed needs a dev build (Tier 3 - foundations in place).
5. Redemption - owner: `POST /coupons/:id/redeem`; any group member on a shared coupon: `POST /groups/:id/coupons/:couponId/redeem`. Body is `{redeem_all:true}` or `{amount:N}` - **never a client-computed absolute balance**: multiple members can redeem the same shared coupon concurrently, so the server applies `SET balance = balance - :amt` with `ConditionExpression balance >= :amt` (atomic, can't overdraw, 409 on conflict - `redeemCouponAmount`, `server/src/repositories/coupons.ts`). Both routes share `server/src/services/redemption.ts`; only authorization differs. Every redemption notifies - `coupon_used` when the coupon is finished (guarded so a repeat call doesn't re-notify), `coupon_partial_redeem` with amount + remaining otherwise; a partial that drains the balance reports as finished. Redeem-all on an already-used coupon returns 409, never a false success (`markCouponUsed` is unconditional, so the route must guard it). Any rejected redeem closes the coupon detail client-side and refreshes the list: a rejection means that screen's copy is stale, and leaving it open invites another attempt against the same stale numbers. Fan-out is `notifyCouponRecipients` (`repositories/groups.ts`), keyed **by user, not by group** - a coupon shared to several groups with overlapping membership must notify each person once; copy stays in the service, fan-out in the repository. `PATCH /coupons/:id` stays the general-purpose **edit** endpoint (absolute writes, correct for editing) and keeps a notify safety net. Notifications must be **awaited before `res.json()`** - Lambda freezes the execution environment once the response returns, so fire-and-forget work after it may never run. Client also calls `NotificationsContext.bump()` after a local redeem so the actor's own other mounted screens refresh without a WS round-trip.
6. Groups & P2P sharing - server manages groups/permissions; coupon code delivered via WebRTC data channel to online recipients (server only relays SDP/ICE signaling, never the code), encrypted DB fallback (72h TTL) for offline recipients or failed P2P negotiations; invitation flow: admin invites → pending_user_ids → invitee accepts/declines via notification panel; admin can rename or delete the group (403 for non-admins)
7. Search - client queries server by store → server returns coupon IDs → client filters locally
8. Gmail coupon scanner - two coexisting connect flows, same backend logic after that: **browser bridge** (works in plain Expo Go) - `POST /gmail/connect/start` mints a signed state token and returns a Google consent URL, opened in the system browser; Google redirects to the public `GET /gmail/callback` (unauthenticated - identifies the user via the state token, not a session), which finishes the exchange and renders a plain HTML result page; `GET /gmail/status` lets the client detect the completed connection after switching back. **Native** (dormant - needs a Dev Client build, since Expo Go can't own the `cuplet://` OAuth redirect scheme; no dev-client build config lives in this repo, so the browser bridge is the only working path. `isGmailOAuthAvailable` gates it at runtime) - `POST /gmail/connect` exchanges a PKCE auth code for tokens server-side (client secret never on device). Either way: `POST /gmail/scan` re-derives an access token (using whichever OAuth client - `oauth_client` - issued that connection's refresh token), runs `users.messages.list` with a keyword `q` filter (never full-inbox download), merges candidate headers into the connection row keyed by `message_id`; `GET /gmail/candidates` returns the list. **Auto-draft extraction:** for each newly-found candidate, `POST /gmail/scan` also fetches the full message body (`getMessageBody`, `format=full`) and runs regex-based `extractCouponFields` (`server/src/lib/gmail.ts`) to best-effort pull a coupon code/store/amount/expiration; these draft fields are returned transiently in the scan response only - **never written to `GmailConnection.candidates`** (invariant above). `POST /gmail/candidates/:messageId/extract` re-runs extraction on demand (message ID must already be in the caller's stored candidates) for candidates the client hasn't cached a draft for yet. `GET /gmail/candidates/:messageId/body` (same ownership restriction) returns the raw email body capped at 4000 chars, on demand only - not bundled into `/scan` - so the user can read the source email before creating a coupon (`GmailEmailPreview.tsx`, opened from a candidate tap in place of a confirm alert). Client caches drafts locally (`gmailDraftStorage.ts`) and shows a candidate as a tappable draft-coupon card only if a code was found and it doesn't match an already-saved local coupon code (`getLocalCouponCodes`); tapping confirms then opens `/(tabs)/add` pre-filled (`fromGmail` param) via `useLocalSearchParams`. Declining or saving permanently dismisses that draft (`dismissDraft`).

## Git Rules
- **One-time per clone: `git config core.hooksPath .githooks`** - installs the `pre-push` guard that refuses direct pushes to `main` and `integration/*`. Needed because IDE push/sync buttons push to the tracked upstream regardless of branch name, which `push.default` does not catch. Deliberate push: `ALLOW_PROTECTED_PUSH=1 git push origin <branch>`.
- Never commit directly to `main`. All work on `feature/<name>` or `fix/<name>` branches.
- Sync with main before starting work and before opening a PR.
- Prefer PRs over direct merges - 3-person team, give teammates review window.
- Commit at meaningful milestones: working feature, bug fix, complete refactor. Never commit broken or mixed-concern changes.
- Commit format: `type: short description` - types: `feat` `fix` `refactor` `chore`
- High-conflict files - coordinate with teammates before touching: `client/services/api.ts`, `client/app/(tabs)/_layout.tsx`, `client/package.json`, `server/package.json`
